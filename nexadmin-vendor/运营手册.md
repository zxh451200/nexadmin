# 发行方运营手册

这份手册是**你（发行方）自己用的**，放在框架仓库的 `nexadmin-vendor/` 下；它不属于框架交付物——`release pack` 与 `nexadmin new` 的排除规则（newSkip）会把整个目录挡在客户包外。给第三方插件作者看的是另一份：`docs/plugin-development.md`。

## 1. 各部分是什么、在哪

| 东西 | 位置 | 谁用 | 作用 |
|---|---|---|---|
| 框架（模板） | `nexadmin/` | 发给客户 | 含授权**验证**（公钥），不含私钥 |
| 授权签发后台 | `nexadmin-vendor/licensor/` | 只有你 | 用私钥签发授权文件 |
| 文档站 | `nexadmin-vendor/docs-site/` | 对外公开 | 文档、插件市场、授权查询 |
| 官方付费插件源码包 | `nexadmin-plugins/` 下九个插件目录，逐项见 [交付核对清单](交付核对清单.md) | 独立交付 | 源码、注册、授权、环境验收分别核对；多语言插件当前有接入阻塞 |
| 私钥 | 你自己选一个安全位置 | 只有你 | **丢了发不出新授权，泄露了别人能自己签授权** |

2026-10-23 assistant 与 identity 补充：原九插件数量为历史范围。assistant 主项目和独立包后端已统一为 1.1.0，命名会话模型及两处三引擎 SQL 使用平台表 `plg_assistant_conversation`、BIGINT 主键，PostgreSQL 索引已修正。实体使用实际存在的 `nexadmin/pkg/idgen.ID`，创建调用 `idgen.Next()`，JSON 为字符串，`idgen.Parse()` 加正数及 `String()` 回比校验 canonical ID；瞬态 run/lease 保留随机 ID。独立库启用该插件时须将表加入 `platform_tables`，不能加入业务 `tables`。独立包前端 `api.ts` 已补齐命名会话 CRUD 和会话选择参数。identity 目录同步使用 `auth.ClaimsFrom(c)`，检查 nil 和非正数用户 ID 后再提交任务；独立包按主项目对齐。两插件生产后端、前端、manifest 和三引擎 SQL 的主副本 diff 无差异，全项目 Go 构建及前端 typecheck 均通过。SQL 尚未执行，持久化真实验收未做，不能把构建或 diff 一致记为整包交付通过；验证结果见《交付核对清单》。

## 2. 第一次上线前（只做一次）

1. **生成正式密钥对**（在你自己的安全机器上）：
   ```bash
   cd nexadmin && go run ./cmd/nexadmin plugin keygen --out ~/secure/nexadmin-license.pem
   ```
   输出里有 `kid` 和公钥 base64，记下来。
2. **私钥保管**：权限设为 0600；至少做两份加密备份，放在不同的地方；不要放进任何 git 仓库、网盘同步目录或服务器的项目目录。
3. **把公钥放进框架**：编辑 `nexadmin/core/plugin/pubkey.go`，把开发公钥换成正式公钥。开发公钥不要留在内置集合里（`release check` 会报）。
4. **同步文档站的授权查询页**：把同一把公钥填进 `docs-site/data/pubkeys.json`，去掉「示例」标注。
5. **清掉开发痕迹**：删除 `nexadmin/.dev-keys/`、`nexadmin/data/licenses/`、模板里已安装的插件目录（当前有九个，按清单和目录枚举全部清理，不要只处理 cron/audit/codegen；特别留意多语言插件的旧目录 `plugins/i18neditor/`）。`plugins/plugins.go` 要保留；用 `go run ./cmd/nexadmin plugin remove <id>` 移除最稳妥，它会同步清掉里面的空导入（数据表与授权文件保留，所以 `data/licenses/` 仍要单独删）。
6. **跑发布检查**：`cd nexadmin && go run ./cmd/nexadmin release check`（加 `--strict` 则 WARN 也算失败），所有 FAIL 清零，并逐条确认它最后打印的人工确认项。自动检查项有：开发公钥仍在、`.dev-keys/`、`data/licenses/*.lic`、`web/.env.production` 缺 `VITE_MOCK=false`、`config/config.yaml`、`data/` 与 `logs/` 残留（WARN）、`plugins/` 下已装插件、`framework_version` 仍是 0.x（WARN）、`.nexadmin.manifest.json` 里列出的路径不存在（精确路径 FAIL，通配路径 WARN）、`go.mod` 本地路径 `replace`、残留 `.bak`/`.orig`、`web/dist` 与 `bin/`（WARN）。

## 3. 每次卖出一份插件

**日常用授权签发后台：**

```bash
cd nexadmin-vendor/licensor
# 一次性：把明文私钥加密成密文文件（交互输入口令两次；自动化可用 LICENSOR_PASSPHRASE）
go run . encrypt-key --in ~/secure/nexadmin-license.pem --out ~/secure/nexadmin-license.enc
go run . decrypt-check --key ~/secure/nexadmin-license.enc   # 只验证口令并打印 kid，不输出私钥
# 确认无误后，自行安全删除明文文件（工具不会自动删除）

# 日常：用密文启动，口令从 LICENSOR_PASSPHRASE 或终端提示读取（错 3 次退出）
export LICENSOR_TOKEN='一个长随机口令'
go run . --key ~/secure/nexadmin-license.enc        # 默认只监听 127.0.0.1:8787，且只允许回环地址访问
```

- 密文用 PBKDF2-SHA256（60 万次以上）+ AES-256-GCM，解密后私钥只在内存里。仍可直接用明文 PEM 启动，但会打印醒目警告。**口令丢了等于私钥丢了**，请和私钥备份一起保管。
- 口令交互输入依赖 `/dev/tty` 和 `stty`（Linux/macOS）；Windows 不支持交互，只能用环境变量 `LICENSOR_PASSPHRASE`。
- 访问控制 `--allow-ip`（逗号分隔的 IP/CIDR，可重复，或环境变量 `LICENSOR_ALLOW_IP`）：默认只允许回环地址；一设置就只允许所列地址（要保留本机请自己写上 `127.0.0.1`）。监听非回环地址却没设 `--allow-ip` 时，程序直接拒绝启动。
- 放在反向代理后面时，加 `--trusted-proxy <代理 CIDR>`：只有来自这些代理的连接才会采信 `X-Forwarded-For`（取最右侧非代理 IP）；否则一律按 TCP 对端地址判定。不在白名单的请求返回空 403，日志只记 IP 和时间。

浏览器打开 `http://127.0.0.1:8787`，输入口令，选插件、填客户名、有效期、域名，点生成，复制或下载 `.lic`，发给客户。客户在「系统管理 → 插件管理」里导入，马上生效。

- 签发记录写在 `licensor/data/issued.json`，**要备份**；它是你续费提醒和对账的依据。
- 页面上可以看 30 天内到期的授权，并导出 CSV。
- 远程访问必须放在带 TLS 的反向代理后面，不要直接把端口开到公网。

**应急用命令行**（后台起不来时）：

```bash
cd nexadmin && go run ./cmd/nexadmin plugin sign \
  --key ~/secure/nexadmin-license.pem --plugin cron \
  --customer "某某公司" --expires 2027-12-31 --domains erp.example.com \
  --out cron-某某公司.lic
```

命令行签发不会写入 `issued.json`，事后要手工补记录。授权序列号默认随机生成（可用 `--serial` 指定，小写字母/数字/连字符，6~64 位），命令会打印出来，请记下：吊销要靠它。

**定价建议**：卖年订阅，有效期别超过一年。授权发出去后只能做离线吊销（见下文「吊销授权」），那只是辅助手段，主要靠短有效期加续费来控制。

## 4. 续期

到期前 30 天在授权后台查「即将到期」，联系客户，收款后用「按旧记录续期」生成新授权，发给客户重新导入即可。授权到期后插件会自动下线（路由返回 403，插件管理页状态为 `expired`；菜单是否随之隐藏：未验证，代码里没找到对应逻辑），数据表保留，续期后恢复。

### 4.1 吊销授权（离线辅助）

1. 日常：授权后台在授权列表里点「吊销」并填原因，再导出吊销清单。应急时用命令行：`go run ./cmd/nexadmin plugin revoke --key <私钥> --serial <序列号> --reason <原因> --out config/license-revoked.json`，它会在现有清单上追加并重新签名。
2. 把最新的 `config/license-revoked.json` 单独发给客户放进 `config/`（或手动放进每次的升级包）。它**当前已在** `.nexadmin.manifest.json` 的 `framework_paths` 中：升级命令会把新包缺失的框架文件移入回收目录。每次打包必须核对包含最新公钥集合与签名吊销清单；漏包可能导致客户已有清单被移走，不能再按“未受升级管理”操作。
3. 客户可以删除清单，所以这只是辅助手段；没有序列号的旧授权不能被单独吊销，主要手段还是短有效期。
4. 签发时记录授权序列号（插件管理页和 `plugin sign` 输出都会显示）。授权后台没有「撤销吊销」，错吊销只能给客户重签新授权。

## 5. 发布框架新版本

1. 先更新 [交付核对清单](交付核对清单.md) 的源码同步、注册、路径和真实环境验收状态，再更新 `.nexadmin.manifest.json` 的 `framework_version`，写好升级说明（没有手动步骤就写「无」）。
2. 跑前后端接口契约核对：`cd nexadmin && go run ./scripts/contract_check`（`--json` 出 JSON，`--out <文件>` 同时落盘，`--warn-only` 让 A 类问题也返回 0）。它对照后端路由、权限码与前端调用 / mock，A 类（前端调用了后端没有的接口）非空时返回非零；B、C 类是提示项，逐条看过再决定。这个脚本在框架源码仓库里跑，`nexadmin new` 和 `release pack` 都不会把它带给客户。
3. 跑 `release check`，确认 FAIL 为零（项目见第 2 节第 6 步）。
4. 打源码包：`cd nexadmin && go run ./cmd/nexadmin release pack [--out <路径.zip>]`。它会先跑一遍 `release check`，有 FAIL 就拒绝打包（`--force` 仅限内部测试，该包不得对外发布）；默认输出到模板目录上一级的 `nexadmin-<framework_version>.zip`，包内根目录是 `nexadmin-<framework_version>/`，打完会打印文件数和 sha256，可直接给 `nexadmin upgrade --from` 使用。排除规则与 `nexadmin new` 共用：`.dev-keys/`、`data/` 与 `logs/`（只留 `.gitkeep`）、`config/config.yaml`、`node_modules/`、`web/dist`、`backup/`、模板里已安装的插件，以及 `scripts/contract_check`、`scripts/derive_check`、`scripts/gen_icons`。`bin/` 不在排除表里，靠 `release check` 的 WARN 提醒先删。不用再手工拼打包命令。
5. 真实数据库验证（可选，当前只覆盖 PostgreSQL）：`nexadmin-vendor/verify-db/run.sh`。它构建 `cmd/server`，用 docker 起临时 `postgres:16-alpine`（只绑定 127.0.0.1），或用环境变量 `PG_HOST`、`PG_PORT`、`PG_USER`、`PG_PASSWORD` 指向已有实例（只建并删除一个 `nexadmin_verify_*` 库），然后依次做非交互 `init`、`migrate --status`、启动并登录读菜单、重启验证迁移与种子幂等、`reinit --dry-run`，最后清理。MySQL / MariaDB 没有对应脚本。
6. 在一台干净机器上用新包验证一遍：`nexadmin new` → 构建 → 启动 → 初始化向导；再用 `nexadmin upgrade --from <新包>` 在一个旧版本项目上升级一次，确认业务区零改动。
7. 发布升级包给客户（路线：CLI 覆盖、git 合并、补丁，见设计文档 §5）；如有吊销清单，按 4.1 节一并放入。

## 6. 换密钥（轮换）

框架支持同时信任多把公钥，但**已经发给客户的框架只认当时内置的公钥**，所以必须分两步：

1. 先生成新密钥，把**新公钥加进**下一个框架版本的内置集合（旧公钥保留），发布框架升级，让客户升级。
2. 大多数客户升级完成后，才开始用新私钥签发新授权。旧私钥签发的授权继续有效，直到到期。

不要在客户还没升级时就改用新私钥签发，那些授权在老版本框架上会校验失败。紧急情况（私钥泄露）见下一节。

## 7. 私钥泄露的应急

授权没有联网吊销，所以泄露后主要靠「让旧钥失效」（离线吊销清单只能按序列号作废单个授权，对整把私钥泄露不够用）：

1. 立刻生成新密钥，发布只信任新公钥的框架补丁版本（从内置集合里移除旧公钥）。
2. 通知所有客户尽快升级，并用新钥重新签发授权给付费客户。
3. 在升级完成之前，旧钥签发的授权（包括别人伪造的）在老版本上仍然有效，这是离线授权无法避免的代价。

所以私钥保管比什么都重要，宁可麻烦也别图方便。

## 8. 接入第三方插件作者

1. 作者按 `nexadmin/docs/plugin-development.md` 开发，提交插件包和说明。
2. 你按该文档第 8 节的清单审核：不改 core、三种数据库迁移齐全、有权限校验、有 mock、无硬编码颜色、无自带授权逻辑、依赖许可证可商用。
3. 通过后在框架的 `config/plugin-market.yaml` 增加条目（repo、分类、价格），跑 `go run ./cmd/nexadmin plugin market sync --docs <docs-site 目录>` 重新生成 `data/plugins.json` 上架；插件源码 push 到 GitHub 仓库后，客户即可在后台「插件市场」一键安装（详见第 11 节）。
4. 买家购买后，由你用自己的私钥签发授权（作者拿不到私钥，这也是你分成结算的依据）。
5. 分成比例、结算周期、退款、维护义务等条款你还没定，定好后补进文档站「购买授权」页和插件开发指南第 10 节。

## 9. 文档站维护

- **同步插件开发指南**：框架里的 `nexadmin/docs/plugin-development.md` 是源，改完要**手工复制**到 `docs-site/plugin-development.md`（两边没有自动同步）。副本第一行是来源注释（`<!-- 来源：手工复制自框架 ... -->`），复制时保留它，其余内容与源文件一致。VitePress 会把正文里的 `{{ }}` 当 Vue 插值、把没包在反引号里的 `<尖括号>` 当 HTML 标签，源文件里这类内容都要放进反引号或代码块，否则构建会报错。
- **上架插件**：市场唯一数据源是框架的 `config/plugin-market.yaml`，文档站展示与后台一键安装都从它来。改完跑 `go run ./cmd/nexadmin plugin market sync --docs nexadmin-vendor/docs-site` 重新生成 `data/plugins.json`（2026-10-25 起已上架全部十个官方 pro 插件，价格均为「待定」）。新增上架前逐项核对 [交付核对清单](交付核对清单.md) 中的接入阻塞和验收项。
- **授权公钥**：换密钥时改 `data/pubkeys.json`。
- **构建**：`cd docs-site && npm run docs:build`，把产物部署到静态服务器。构建会在 `docs-site/.vitepress/` 下生成 `dist` 与 `cache`，部署后可以删掉（保留 `node_modules`）。

## 11. 插件市场统一管理

市场的唯一数据源是框架的 `config/plugin-market.yaml`，三个消费方都从它来：

| 消费方 | 读法 | 用途 |
| --- | --- | --- |
| 后台「插件市场」Tab | 运行时 `GET /api/v1/plugins/market` | 客户浏览、一键安装（下载 GitHub zipball → 装入源码树 → 重建 → 自重启） |
| 文档站市场页 | `plugin market sync` 生成的 `data/plugins.json` | 对外展示（名称/版本/价格） |
| 安装校验 | 目录条目与插件包 plugin.yaml 在安装时交叉校验 | 目录写错装不进去，防造假 |

上架/更新一个插件：

1. 插件源码包从已安装插件直接再生：`go run ./cmd/nexadmin plugin pack --out <id>-<version>.zip <id>`（产出 `plugin.yaml + backend/ + web/` 的 zip，与 install 输入格式互逆；把 zip 内容 push 到 GitHub 仓库即可）；
2. 在 `config/plugin-market.yaml` 增改条目（repo 填实际 owner/name，价格与分类同步更新）；
3. 跑 `go run ./cmd/nexadmin plugin market sync --docs nexadmin-vendor/docs-site` 刷新文档站；
4. 客户侧后台「插件市场」即可一键安装；付费插件靠运行期授权闸门收费（签发见第 3 节），源码可见不等于可用。

私有仓库：条目加 `token_env`，客户运行环境配同名环境变量（GitHub PAT），下载时自动带上。国内访问 GitHub 不稳时：把发行包 zip 放到 OSS/自有服务器，条目改填 `url` 直链（与 repo 二选一，安装器优先用直链）。

**monorepo 模式（推荐，1 个仓库装全部插件）**：GitHub 建 1 个 `nexadmin-plugins` 仓库，每个顶级目录一个插件；目录条目用 `repo + subdir + ref` 指向它。推送脚本：`scripts/push-plugins.cmd <账号>`（monorepo 本地副本默认在主仓库旁的 `../nexadmin-plugins/`）。

**第三方作者上架与售卖的管理**（作者写插件到你平台卖）：

1. **审核准入**：作者按 `docs/plugin-development.md` 开发，提交源码包（发 zip 或向你申请仓库分支）；你按开发指南的审核清单人工审（不改 core、三引擎迁移齐全、权限校验、mock、无自带授权逻辑、依赖许可证可商用）——插件与框架同进程运行，人工审核是安全底线，不可省。
2. **登记上架**：审核通过的插件进 monorepo（或保留在作者自己的 GitHub 仓库），`plugin-market.yaml` 加条目；关键约束是 **ref 钉死到你审核过的那个 tag**——作者后续推了什么，客户装不到，除非你复审后改 ref。
3. **代收代付**：授权必须由你的 licensor 私钥签发（框架只信你的公钥集合），收款进你的账户，按约定比例给作者分成——签发记录（`issued.json`）就是对账与分成的依据。作者拿不到私钥，这是平台权力的根基。
4. **更新与下架**：作者发新版 → 你复审 diff → 改目录 `ref` → sync；发现作恶：目录移除 + `plugin revoke` 按序列号吊销已发授权。
5. **演进**：量小（几十个内）手工维护 yaml 足够；量起后把目录文件迁到独立仓库，作者提 PR 上架（PR 即审核工单），合并自动触发 sync；收款自动化可复用框架自带 payment 插件对接。
