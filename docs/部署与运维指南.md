# NexAdmin 部署与运维指南

面向部署和运维人员。内容来自 `scripts/`、`deploy/`、`core/ctl`、`core/setup`、`core/migrate`、`cmd/server` 的代码与脚本。2026-10-23 本轮仅静态读取代码并更正文档，未运行应用命令、测试、编译、SQL 或真实验收；下文“本机实测”等为历史记录，不代表当前代码已复验。编译通过也不代表真实数据库、Redis 多实例、浏览器或身份源链路验收通过，涉及这些环境的步骤仍需单独验收。

约定：除特别说明，命令都在项目根目录（含 `config/`、`migrations/` 的目录）执行。程序按当前工作目录找 `config/default.yaml`、`config/config.yaml`、`data/`、`logs/`、`migrations/`。

## 1. 运行形态

- 单一二进制：`scripts/build.sh` 用 `-tags embedweb` 把前端产物 `web/dist` 嵌入 `nexadmin-server`，同一个端口同时提供 `/api/v1`、`/healthz`、`/metrics` 和前端页面（前端路由回退到 `index.html`，`/assets/` 带 hash 的文件按 immutable 缓存，`sw.js`、`manifest.webmanifest`、`offline.html` 不缓存）。
- 不带 `embedweb` 构建（`go run ./cmd/server`、`go build ./cmd/server`）：不托管前端，未命中的路径返回 JSON 404。这是开发模式，前端另起 vite。
- 开发模式：`go run ./cmd/server` 起后端（`app.env=dev` 时日志输出到控制台，CORS 放行任意 Origin）；`cd web && npm run dev` 起前端，端口 5173，`/api` 代理到 `http://127.0.0.1:8080`。`web/.env.development` 设置了 `VITE_MOCK=true`，前端代码里仅当 `VITE_MOCK === 'true'`（统一由 `web/src/framework/env.ts` 判定）才加载 mock 数据；变量未设置视为关闭，所以开发模式靠 `.env.development` 显式写 `true`，生产构建靠 `.env.production` 的 `false`（漏配也不会跑假数据）。要连真实后端，按 Vite 的约定可以用命令行环境变量覆盖：`VITE_MOCK=false npm run dev`（未实测）。
- 运行所需文件：`nexadmin-server`、`config/default.yaml`、`migrations/`（`framework/` 和 `business/`）。`config/config.yaml`、`data/`、`logs/` 由向导或运行时创建。实测：只有 `config/default.yaml` 的空目录里可以启动未初始化的服务；初始化之后找不到 `migrations/framework` 会报错（见第 13 节）。
- 前台运行：`./nexadmin-server`（Ctrl+C 或 SIGTERM 优雅退出，最长等待 10 秒）。后台运行：`start | stop | restart | status`（第 4 节）。正式生产建议交给 systemd 或容器编排。

## 2. 构建与打包

### 2.1 scripts/build.sh（Linux / macOS）

```
sh scripts/build.sh
```

脚本内容（已逐行核对）：读取 `.nexadmin.manifest.json` 的 `framework_version`（读不到则退出）→ `cd web && npm ci && npm run build` → `go build -trimpath -tags embedweb -ldflags "-s -w -X main.version=<版本>" -o bin/nexadmin-server ./cmd/server`。不依赖 make。

前置：Go（`go.mod` 声明 `go 1.25.0`）、Node 与 npm（Dockerfile 用 `node:22-alpine`）。

核对情况：本机跑通了 `npm run build`（`tsc --noEmit && vite build`）和同样参数的 `go build -tags embedweb`，产出的二进制 `version` 输出 `0.1.0`，启动后访问 `/` 返回 `text/html`。`npm ci` 需要联网，本机未执行。

### 2.2 scripts/build.bat（Windows）

同样的三步，版本号用 PowerShell 读取清单，产物 `bin\nexadmin-server.exe`。未在 Windows 上运行。

### 2.3 deploy/Dockerfile

构建上下文是项目根目录：

```
docker build -f deploy/Dockerfile -t nexadmin:latest .
```

多阶段：`node:22-alpine` 构建前端 → `golang:1.25-alpine` 以 `CGO_ENABLED=0 go build -tags embedweb` 构建 → `alpine:3.20` 运行。运行镜像要点（逐行核对）：

- 非 root 用户 `nexadmin`（uid/gid 10001）；工作目录 `/app`。
- 二进制 `/app/nexadmin-server`；`/app/migrations` 随镜像；默认配置放在 `/app/defaults/default.yaml`。
- 入口 `/app/entrypoint.sh`：每次启动先把 `/app/defaults/default.yaml` 覆盖拷贝到 `/app/config/default.yaml`（升级镜像即升级默认值），再 `exec /app/nexadmin-server "$@"`，所以 `docker run <镜像> init --config ...` 可以直接带子命令。
- 运行镜像（`alpine:3.20`）除 `ca-certificates`、`tzdata` 外还装了 `mariadb-client`（提供 `mysqldump` / `mysql`，MySQL 与 MariaDB 通用）和 `postgresql16-client`（提供 `pg_dump` / `psql`，对应 compose 里的 `postgres:16`；Alpine 3.20 没有不带版本号的 `postgresql-client` 包名），页面备份、`reinit` 的备份和 `restore` 依赖它们（第 7 节）。
- 卷：`/app/config`、`/app/data`、`/app/logs`；暴露 8080；`HEALTHCHECK` 用 `wget` 访问 `http://127.0.0.1:8080/healthz`（未改动）。
- 备份目录：镜像里建好并授权 `/app/data/backup`（`nexadmin` 用户可写，在 `data` 卷内），并设 `ENV NEXADMIN_BACKUP_DIR=/app/data/backup`。注意环境变量优先于 `config.yaml`，想改目录请改这个环境变量（或在 compose 里覆盖），不要只改 `config.yaml` 的 `backup.dir`。备份页、`reinit` 和 `restore` 用同一个目录。

核对情况：包名来自 Alpine 3.20 软件包索引（`mariadb-client` 含 `/usr/bin/mysqldump`、`/usr/bin/mysql`；`postgresql16-client` 存在）；镜像本身未构建、未实机验证。

### 2.4 deploy/docker-compose.example.yml

```
# 项目根目录写 .env：POSTGRES_PASSWORD=...（必填）
docker compose -f deploy/docker-compose.example.yml up -d --build
docker compose -f deploy/docker-compose.example.yml --profile cache up -d   # 同时启用 valkey
# 首次部署用非交互初始化（容器内不开放远程向导）
docker compose -f deploy/docker-compose.example.yml run --rm app init --config /app/config/init.yaml
```

文件内容（逐行核对）：服务 `app`（`context: ..`，`dockerfile: deploy/Dockerfile`，端口 `8080:8080`）、`postgres`（`postgres:16`，带 `pg_isready` 健康检查，`app` 依赖它 healthy）、`valkey`（`valkey/valkey:8`，仅 `--profile cache` 启动，密码 `VALKEY_PASSWORD`，默认值 `change-me`）。`app` 的环境变量：`NEXADMIN_APP_ENV=production`、`NEXADMIN_DATABASE_TYPE=postgres`、`..._HOST=postgres`、`..._PORT=5432`、`..._USER=nexadmin`、`..._PASSWORD=${POSTGRES_PASSWORD}`、`..._NAME=nexadmin`，以及 `NEXADMIN_BACKUP_DIR=/app/data/backup`（镜像里已默认，写出来便于查看）；文件里还有一条注释掉的 `NEXADMIN_SERVER_TRUSTED_PROXIES` 示例，前面有反向代理时必须配置（第 11.1 节）。使用 valkey 时需自行加 `NEXADMIN_CACHE_DRIVER=redis`、`NEXADMIN_CACHE_ADDR=valkey:6379`，以及 `NEXADMIN_CACHE_PASSWORD`（文件注释只提了前两项，密码项来自配置键 `cache.password` 与 valkey 的 `--requirepass`）。四个具名卷 `nexadmin_config`、`nexadmin_data`、`nexadmin_backup`、`nexadmin_logs` 对应 `/app/config`、`/app/data`、`/app/data/backup`（备份单独一个卷，挂在 data 卷里面的子目录上，便于定期拷走）、`/app/logs`。

`init --config /app/config/init.yaml` 要求这个文件已经在 `nexadmin_config` 卷里（格式见第 3.2 节）。样例里的 `postgres` / `valkey` 密码、镜像版本在生产环境必须替换并固定。

核对情况：本机的 Docker 没有 `compose` 子命令，也没有守护进程，`docker compose config` 和镜像构建都没能运行，只做了人工核对。

### 2.5 deploy/nexadmin.service（systemd）

安装步骤（取自文件头注释）：

```
useradd -r -s /usr/sbin/nologin nexadmin
mkdir -p /opt/nexadmin/{bin,config,data,logs,backup}      # 放入 bin/nexadmin-server、config/default.yaml、migrations/
chown -R nexadmin:nexadmin /opt/nexadmin/{config,data,logs,backup}
cp deploy/nexadmin.service /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now nexadmin
```

环境文件 `/etc/nexadmin/nexadmin.env`（权限 0600，root 所有），例如 `NEXADMIN_APP_ENV=production`、`NEXADMIN_DATABASE_PASSWORD=...`。单元要点：`User/Group=nexadmin`，`WorkingDirectory=/opt/nexadmin`，`ExecStart=/opt/nexadmin/bin/nexadmin-server`，`Restart=on-failure`，`RestartSec=5`，`LimitNOFILE=65536`；加固项 `NoNewPrivileges`、`ProtectSystem=strict`、`ProtectHome`、`PrivateTmp`、`PrivateDevices`、`ProtectKernel*`、`ProtectControlGroups`、`RestrictSUIDSGID`、`RestrictRealtime`、`LockPersonality`；只有 `config`、`data`、`logs`、`backup` 四个目录可写（`ReadWritePaths`，安全加固项都保留）。

注意（未实机验证）：`backup` 目录必须事先存在，否则 `ReadWritePaths` 里的这一项会让单元启动失败（systemd 的命名空间设置报错），所以上面的 `mkdir` 要包含它。默认 `backup.dir=./backup` 解析到 `WorkingDirectory` 下的 `/opt/nexadmin/backup`，正好是这个可写目录；改了 `backup.dir` 要同步改 `ReadWritePaths`。宿主机上要自己装数据库客户端（例如 `apt install mariadb-client postgresql-client`），单元不负责。`migrations/` 要放在 `/opt/nexadmin/migrations`（工作目录下）。

核对情况：本机 `systemd-analyze verify` 版本过旧，不认识 `ProtectKernelTunables` 等指令，没能完成校验；单元未在 systemd 下启动过。

## 3. 初始化

### 3.1 向导（浏览器）

未初始化时服务照常启动，只开放向导和状态接口：

- 业务 API 统一返回 HTTP 503，`{"code":503,"message":"系统尚未初始化","data":null,"reason":"NOT_INITIALIZED"}`（本机实测）。`/healthz`、`/metrics`、`GET /api/v1/system/status`（返回 `{"initialized":false}`）、`GET /api/v1/i18n/languages`、`/api/v1/setup/*` 可用。
- 控制台（后台启动时是 `logs/nexadmin.out`）打印向导地址和一次性初始化令牌。`start` 的输出里也会带上它。
- 默认只允许本机访问向导。“本机”要求 TCP 对端为回环地址，且没有 `X-Forwarded-For`、`X-Real-IP`、`Forwarded`、`X-Forwarded-Host` 转发头。同机 nginx 转发来的请求也视为代理请求。远程或代理初始化须配置 `setup.allow_remote: true`，并在页面输入控制台的一次性令牌，或由 API 客户端添加 `X-Setup-Token`。本机直连无转发头时不需要令牌。
- 向导共 6 步：环境检查 → 数据库 → 缓存 → 管理员与站点 → 可选配置 → 确认执行。数据库和缓存支持连接测试，S3 与 AI 提供配置输入但没有独立连通性探测。
- 执行 `POST /api/v1/setup/execute`，依次完成 `writeConfig`（写 `config/config.yaml`，权限 0600）→ `migrate` → `seed` → `createAdmin` → `writeMark`（写 `data/.initialized`）。任一步失败，已写入的 `config.yaml` 会回滚，可改参数重试；同一时刻只允许一个初始化在跑。页面通过 POST SSE 接收阶段真实进度，普通 API 客户端保持 JSON 兼容。反向代理需允许 SSE 即时透传。
- 远程初始化令牌仅存组件内存，成功后清空，不写浏览器存储。
- 管理员校验：用户名 `^[A-Za-z][A-Za-z0-9_]{2,31}$`；密码**没有强度规则**，只要求非空且不超过 72 字节（bcrypt 只取前 72 字节，超出会被截断，所以拒绝；后端 `passwordAcceptable`）；站点名非空且不超过 60 个字符；时区必须是有效 IANA 名；语言必须在 `languages` 里。站点名写入设置页「站点」分区（`sys_setting` 的 `site.siteName`，在 `seed` 步骤里写，可重复执行），登录页、顶栏和 PWA manifest 显示的就是它；同时也写进 `config.yaml` 的 `app.name`，但那一项只作日志 / 默认名称用途，页面不读它。
- 初始化时各模块的 `Seed` 除了菜单、字典、参数、角色等出厂数据，还会写入演示数据：演示用户（创建时没有写密码字段，按代码推断不能用密码登录，未实测）、部门、岗位、通知公告、消息、日志、演示租户与套餐、出厂角色（`operator`、`auditor`、`editor`、`guest`、`secadmin`）。这些行“不存在才插入，已存在一律不动”，且 `Seed` 只在初始化时跑，不在每次启动跑（每次启动只补菜单等 `StartupSeeder` 项）。上线前请按需清理演示数据（具体清单见各模块的 `Seed`，未逐表核对）。
- 初始化完成后向导路由在已初始化的进程里根本不注册，`/api/v1/setup/*` 不再可用；服务原地切换到完整路由，无需重启。
- “是否已初始化”的判定（`setup.IsInitialized`）：`data/.initialized` 存在 → 已初始化；`config/config.yaml` 不存在 → 未初始化；否则连数据库看有没有管理员，连不上、读不到都按已初始化处理（只有库可连通且一张表都没有时判未初始化，`reinit` 之后就是这种情况）。

### 3.2 非交互初始化（容器 / 自动化）

```
./nexadmin-server init --config init.yaml
```

文件可以是 JSON 或 YAML，内容与向导 `POST /api/v1/setup/execute` 的请求体相同，字段名如下（字段名取自 `core/setup/request.go`）：

```yaml
db:
  type: postgresql        # mysql | mariadb | postgresql
  host: 127.0.0.1
  port: 5432
  username: nexadmin
  password: "<数据库密码>"
  database: nexadmin      # 只允许字母、数字、下划线，最长 64
  autoCreate: false       # true：库不存在则创建
cache:
  type: memory            # memory | valkey（也接受 redis）
  # addr: valkey:6379     # valkey / redis 时必填
  # password: ""
admin:
  username: admin
  password: "<非空，不超过 72 字节；没有强度规则>"
  siteName: NexAdmin
  language: zh-CN
  timezone: Asia/Shanghai
optional:                 # 可整段省略
  storage: local          # local | s3
  # s3Endpoint / s3Bucket / s3AccessKey / s3SecretKey / s3Region / s3Prefix / s3PathStyle
  # aiEnabled / aiBaseUrl / aiApiKey / aiModel
```

行为（本机用无数据库的环境实测了校验和失败路径）：

- 逐步打印 `writeConfig` / `migrate` / `seed` / `createAdmin` / `writeMark` 的状态，不打印密码；任一步失败退出码非 0，报 `init failed at <步骤>: <原因>`，已写入的 `config/config.yaml` 回滚。
- 管理员密码为空或超过 72 字节时报 `init failed at writeConfig: admin password must be 1-72 bytes`（不再有强度规则；错误文本里与密码相同的片段会被替换成 `***`）。
- 数据库连不上时报 `init failed at migrate: database: connect postgres 127.0.0.1:5432: ...`。
- 系统已初始化（或无法确认未初始化）时拒绝：`系统已初始化（或无法确认未初始化），拒绝重复初始化；如需恢复出厂请用 reinit`。
- 缺 `--config` 时报 `init 需要 --config <文件>`。
- 初始化成功的完整流程（连真实库建表、种数据、建超管）：未实机验证。

## 4. 一键启停

### 4.1 脚本

`deploy/` 下有 `ctl.sh`（Linux）、`ctl.command`（macOS）、`ctl.bat`（Windows）和对应的 `reinit.*`。它们只是薄壳：没有终端就开一个（Linux 依次尝试 `x-terminal-emulator`、`gnome-terminal`、`xterm`），在脚本所在目录或其上一级找 `nexadmin-server`，都找不到且有 `go.mod` 和 `go` 时回退 `go run ./cmd/server`，调用完暂停等待回车。

- `ctl.*` 菜单只有四项：`1 启动  2 停止  3 重启  4 状态`，对应 `start` / `stop` / `restart` / `status`。
- `reinit.*` 直接执行 `nexadmin-server reinit`，可附加参数，例如 `deploy/reinit.sh --dry-run`。
- `init`、`migrate`、`restore`、`version` 没有脚本入口，直接用二进制。

### 4.2 nexadmin-server 子命令

下面的用法按 `cmd/server/main.go` 的参数解析与调用核对（本轮未执行 usage）：

| 命令 | 作用 |
| --- | --- |
| （无） | 前台运行 |
| `version`（或 `--version`） | 打印版本号；不带 ldflags 构建时是 `dev`，`build.sh` 构建的是清单里的 `framework_version`（当前 `0.1.0`） |
| `start` | 后台启动：日志追加到 `logs/nexadmin.out`（权限 0600），写 `data/run/nexadmin.pid`（JSON：pid、端口、关停令牌、启动时间，权限 0600），最多等 20 秒就绪。已在运行则提示 `已在运行（端口 N）`。未初始化时输出向导地址与初始化令牌 |
| `stop` | 通过回环地址上的 `POST /api/v1/system/shutdown`（请求头 `X-Shutdown-Token`）优雅退出，不依赖信号，Windows 与 Linux 一致；最多等 20 秒。没有 pid 文件但服务在运行时报错 `服务在运行，但不是由 start 启动的（没有 pid 文件），请到它所在的终端按 Ctrl+C 停止` |
| `restart` | `stop` 再 `start` |
| `status` | 打印 状态 / pid / 监听地址 / 是否已初始化；未运行时打印 `状态:     已停止` |
| `init --config <文件>` | 非交互初始化（第 3.2 节） |
| `migrate [--tenant platform或租户ID] [--status] [--dry-run] [--mark-applied <scope>/<文件名>] [--unmark <scope>/<文件名>] [--yes]` | 迁移（第 5 节）；省略 tenant 默认平台及全部配置租户 |
| `backup --output <新目录>` | 平台及全部配置租户的完整 SQL bundle（第 7.3 节） |
| `restore-bundle --dir <目录> [--tenant <ID>] (--dry-run 或 --yes)` | 完整校验后顺序恢复，必须停服务；两个执行选项恰选一个（第 7.3 节） |
| `restore <备份文件> [--yes] [--dry-run] [--sha256 <值>] [--platform-only]` | 单平台库恢复；隔离模式必须明确 platform-only（第 7 节） |
| `reinit [--dry-run] [--platform-only]` | 恢复出厂；隔离模式必须明确 platform-only，仍清理共享资源（第 8 节） |

本机在无数据库环境实测了 `start` → `status` → `restart` → `stop` → `status` 的完整循环，以及 `migrate --dry-run`（未初始化时输出 `系统尚未初始化，无需迁移（初始化向导 / init 会自动建表）`）、`reinit --dry-run`（没有 `config/config.yaml` 时输出 `没有 config/config.yaml，说明还没有初始化过，无需恢复出厂`）、`restore --dry-run`（连不上库时报 `连不上数据库，已中止`）。

## 5. 数据库迁移

### 5.1 规则

迁移运行器（`core/migrate`）把三类迁移用同一套规则执行，已执行的文件记录在版本表 `sys_migration`：

| scope | 目录 | 说明 |
| --- | --- | --- |
| `framework` | `migrations/framework/<引擎>/` | 框架迁移，随升级覆盖；必须存在 |
| `business` | `migrations/business/<引擎>/` | 业务迁移；目录不存在视为没有 |
| `plugin:<id>` | 插件自己的迁移目录 | 仅已授权并挂载的插件 |

- `<引擎>` 是 `mysql`、`mariadb`、`postgres`；MariaDB 没有专属目录时回退到 `mysql` 目录。框架目录现在三个引擎各有 24 个文件，业务目录由 `nexadmin add module` 生成 `mysql`、`mariadb`、`postgres` 三份。
- 每个 scope 内按文件名排序，只执行版本表里没有记录的文件；scope 的先后顺序是 framework → business → 插件。
- SQL 按分号切分，`--` 开头的注释行被忽略，文件里不要写含分号的字符串。
- PostgreSQL 每个文件一个事务，失败整体回滚；MySQL / MariaDB 的 DDL 无法回滚，逐条执行，失败时报告 `已执行 N/M 条，第 N+1 条失败，该文件未记录，需先手工修复`。
- 多实例同时启动：靠数据库级锁（MySQL / MariaDB 用 `GET_LOCK`，PostgreSQL 用 `pg_try_advisory_lock`），拿到锁后重新比对版本表，别的实例已做完的直接跳过；等锁最长 2 分钟，超时报 `migrate: 等待迁移锁超时（2m0s），另一个实例可能仍在迁移`。
- 迁移里出现 `INSERT` / `UPDATE` / `DELETE` 只给 WARN，不阻断（出厂数据应由各模块的种子在启动时幂等补齐，不是迁移）。

### 5.2 auto_migrate 与 migrate 命令

- `app.auto_migrate=true`（默认）：每次启动在持锁状态下执行待迁移文件，再幂等补齐出厂数据（菜单等）。
- `app.auto_migrate=false`（生产想把升级与启动分开）：启动时只检查，有待执行迁移就拒绝启动，报 `有 N 个待执行迁移（framework/xxx.sql, ...），app.auto_migrate=false，请先运行 nexadmin-server migrate`。升级后先运行 `nexadmin-server migrate` 再启动。

以上默认描述平台迁移。开启 `database.isolation.enabled` 后，已初始化服务的租户库自动迁移要求 `app.auto_migrate && database.isolation.auto_migrate`，后者默认 `false`；任一关闭时仍检查租户待迁移，有待执行项则拒绝启动。向导 / `init` 显式执行平台迁移，租户部分仅按 isolation.auto_migrate 执行或检查；手动 `migrate` 不受自动开关限制。平台执行框架与 platform 目标迁移，租户执行 business 与 tenant 目标迁移，未明确目标的附加迁移源会被拒绝；每库分别记录并加锁，不是跨库原子迁移，也不会搬迁已有数据。

`migrate --tenant platform` 仅处理平台，`migrate --tenant <规范租户ID>` 仅处理该配置租户；可与 `--status`、`--dry-run` 组合，省略则依次处理平台与全部配置租户。独立库存在时，`--mark-applied` / `--unmark` 必须指定 `--tenant`，防止误标多个库。`migrate --dry-run` 仍需要数据库连接和迁移状态读取，不能当作离线校验；与下文不执行数据库命令的 `restore-bundle --dry-run` 不同。

| 命令 | 作用 |
| --- | --- |
| `nexadmin-server migrate` | 执行全部待迁移；没有则输出 `迁移已是最新` |
| `nexadmin-server migrate --status` | 按 scope 列出 `已执行` / `手工标记` / `待执行` / `CHECKSUM 异常`（每行带 checksum 前 12 位），末尾汇总 `已执行 N，待执行 N，checksum 异常 N`；有异常时退出码非 0 |
| `nexadmin-server migrate --dry-run` | 只列出将执行的文件和语句数，不改库，输出 `共 N 个待执行迁移（dry-run，未改动数据库）` |
| `nexadmin-server migrate --mark-applied <scope>/<文件名> [--yes]` | 迁移中途失败（MySQL DDL 无法回滚）、你已手工把库修好后，把该文件标记为已执行，不运行其中任何 SQL；需交互确认，默认 N，`--yes` 跳过。`<scope>` 是 `framework`、`business` 或 `plugin:<id>` |
| `nexadmin-server migrate --unmark <scope>/<文件名> [--yes]` | 撤销手工标记，该文件重新变为待执行；只能撤销手工标记的记录，真实执行的记录拒绝撤销 |

`--mark-applied` 会拒绝：文件在磁盘上不存在、版本表已有记录（`已在版本表中记录，拒绝重复标记`）、已有记录但 checksum 异常。标记动作带操作者（系统用户名@主机名）和时间写日志。`--mark-applied` 与 `--unmark` 不能同时用。系统未初始化时所有 `migrate` 变体都只输出“无需迁移”。

迁移类命令（`migrate`、`--status` 等）依赖真实数据库，本机只实测了未初始化时的输出，其余按代码核对，未实机验证。

### 5.3 checksum 规则

- 每个迁移文件的指纹是内容的 sha256（先把 `\r\n` 统一成 `\n`，避免 git autocrlf 误报），首次执行时写入版本表。
- 已执行的文件内容之后被改过（违反“只增不改”），启动和 `migrate` 都会拒绝，报：`迁移文件在执行后被修改（违反“只增不改”），拒绝启动: framework/xxx.sql, ...。请还原这些文件，需要的改动请新增后续迁移文件`。处理办法：还原该文件，把结构变更写进下一个编号的新 SQL。
- 不要为了“修”checksum 去改版本表；真正需要跳过某个文件时用 `--mark-applied`。

### 5.4 存量库基线

某个 scope 在版本表里一条记录都没有（例如升级前就已经建好表的库）时，该 scope 的未记录文件按“基线”处理：对 `CREATE TABLE` 的目标表已存在的，跳过该表及其后面的索引语句；文件里的语句全部被跳过则只记录不执行，日志为 `迁移已记录（表已存在，基线）`，`--dry-run` 显示为 `将记录 <scope>/<文件> （表已存在，不执行）`。第一个 `CREATE TABLE` 之前的语句无从判断，照常执行。基线之后该 scope 恢复严格模式。旧的 `sys_plugin_migration` 表里的插件记录会被直接导入。

## 6. 数据需要单独备份的东西

数据库备份（第 7 节）只含数据库。下面这些不在其中，需要自己备份，并且要和数据库备份保持对应：

| 路径 | 内容 | 说明 |
| --- | --- | --- |
| `data/secret.key`（或环境变量 `NEXADMIN_SECRET_KEY`） | 静态加密主密钥 | 丢失后库里已加密的值（第三方密钥、SMTP 密码等）无法恢复 |

| `config/config.yaml` | 本站配置（含数据库密码） | 权限应为 0600 |

## 7. 备份与恢复

### 7.1 备份（页面）

“系统管理 → 数据备份”（模块名 `backup`，权限码 `backup:list` / `backup:edit` / `backup:download`，另外要求超管）。立即备份是异步的，页面轮询列表看结果；也可设置定时。

- 依赖本机命令行工具：MySQL / MariaDB 用 `mysqldump`（或 `mariadb-dump`），PostgreSQL 用 `pg_dump`。找不到时报 `本机未找到 mysqldump / mariadb-dump，请安装对应数据库客户端工具并加入 PATH`（pg 对应 `pg_dump`）；定时来源会在列表里留一条失败记录。
- 文件名 `nexadmin-<引擎>-v<框架版本>-<yyyymmdd-hhmmss>.sql.gz`，同目录下有 `.sha256` 旁路文件；目录权限 0700，文件 0600；先写 `.tmp` 再改名，失败不留半成品。数据库密码通过环境变量 `MYSQL_PWD` / `PGPASSWORD` 传给子进程，不出现在命令行、日志和错误文本里。
- 目录由 `backup.dir` 决定；保留策略 `backup.keep_days`（30）、`backup.keep_count`（10）和定时 `backup.schedule`（`HH:MM`，按 `app.timezone`）仅首次启动作为初始值，之后以页面设置为准（存在 `sys_backup_setting`，多实例共享）。
- 多实例：同一时刻只允许一个备份在跑（记录里有未超时的 `running` 也算忙）；定时靠数据库里的“今天已被某实例抢占”标记，多实例同时到点只有一个会成功。

### 7.2 恢复（只有命令行）

恢复不提供网页入口：

以下单文件示例适用于非隔离模式；隔离模式下 `restore`（包括 `--dry-run`）与 `reinit` 必须显式加 `--platform-only`，仅操作平台库，不会恢复租户业务库。完整配置库集应使用第 7.3 节的 bundle 命令。

```
nexadmin-server stop
nexadmin-server restore backup/nexadmin-mysql-v0.1.0-20261020-120000.sql.gz --dry-run   # 先看清单
nexadmin-server restore backup/nexadmin-mysql-v0.1.0-20261020-120000.sql.gz
nexadmin-server start
```

执行顺序和保护（`core/ctl/restore.go`）：

1. 只接受本系统生成的 `.sql.gz`；服务在运行则拒绝（`--dry-run` 除外）：`服务正在运行，已拒绝恢复；请先执行 stop 停止服务（恢复会覆盖线上数据）`。
2. 校验 sha256：期望值来自 `<备份文件>.sha256` 旁路文件，或 `--sha256 <值>`；两者都没有就拒绝，不做“盲恢复”；校验失败报错并保证未改动数据。
3. 要求本机有导入工具（`mysql` / `mariadb` 或 `psql`）和备份工具（`mysqldump` / `pg_dump`，用于恢复前备份），缺一则中止。
4. 打印清单：将覆盖的库（引擎、主机、端口、库名，当前表数、行数、大小）；备份中包含的表会被删除后重建，备份里没有的表保留。
5. 交互确认 `确认恢复？[y/N]`，只有 `y` 才继续；`app.env=production` 时还要再输入库名；`--yes` 跳过确认（自动化）。
6. 先做一份“恢复前备份”（`nexadmin-pre-restore-<引擎>-v<版本>-<时间>.sql.gz`，写到 `backup.dir`），失败则中止；再导入。导入失败时提示 `库可能处于部分恢复状态；恢复前备份在 <路径>，可用 restore 回滚`。

恢复流程依赖真实数据库与客户端工具，本机未实机验证（本机没有这些工具）。

### 7.3 平台及租户库 bundle（仅静态核对，未执行）

`backup --output <新目录>` 按配置导出平台及全部租户库；父目录必须已存在，输出目录必须尚不存在，路径不能含 `..` 或符号链接。输出含各库 `.sql.gz`、`.sha256` 和 `manifest.json`（目标、大小、sha256；不含连接凭据或密码环境变量名）。备份为顺序独立 dump，**不是跨库原子快照**；需要一致时间点时应由运维安排暂停相关写入。失败保留不完整目录，不能把它当作完整可恢复 bundle。

命令格式如下，仅用于操作说明，本轮未执行（`123` 应换成已配置的规范租户 ID）：

```text
nexadmin-server backup --output /absolute/existing-parent/new-bundle
nexadmin-server stop
nexadmin-server restore-bundle --dir /absolute/existing-parent/new-bundle --dry-run
nexadmin-server restore-bundle --dir /absolute/existing-parent/new-bundle --tenant 123 --dry-run
nexadmin-server restore-bundle --dir /absolute/existing-parent/new-bundle --tenant 123 --yes
```

恢复必须恰选 `--dry-run` / `--yes`，没有隐式交互执行模式。默认恢复全部；`--tenant <ID>` 只导入该租户，不接受 `platform`，但仍校验完整 bundle 和全部配置目标，也仍需全部库的密码环境变量、dump / import 客户端工具。会核验成员路径、大小、sha256、gzip、引擎及配置目标，不能把 bundle 当作自动重映射到不同目标的工具。

即使 `--dry-run` 也要求服务已停止且无 PID 文件；它校验本地文件和工具，不连接数据库、不执行数据库命令、不创建文件。实际 `--yes` 导入前，`backup.dir` 必须已存在且路径无符号链接；先为**全部配置库**生成并校验 `pre-restore-bundle-*` 恢复前 bundle（单租户恢复也如此），失败不开始导入。此后重新校验输入，再顺序导入选中库；dump 中没有的 SQL 对象不会自动删除。失败可能部分恢复，不自动回滚，会报告已完成目标和恢复前备份目录；服务保持停止，需按结果人工恢复和验收后再决定启动。SQL bundle 不含密钥、配置、授权及上传文件，这些仍按第 6 节单独备份。

## 8. 恢复出厂（reinit）

隔离模式必须使用 `reinit --platform-only`（预览同样需要该选项）。它仅重置平台数据库，**仍会清理共享缓存、上传文件和初始化状态**；按当前流程保留 `config/config.yaml`、密钥等文件，具体清理项见下方。它不是“只影响一个租户”的操作，也不会重置租户业务库。

```
nexadmin-server reinit --dry-run     # 或 deploy/reinit.sh --dry-run
nexadmin-server reinit
```

要求 `config/config.yaml` 已存在，否则报 `没有 config/config.yaml，说明还没有初始化过，无需恢复出厂`。流程（`core/ctl/reinit*.go`）：

- 先只读生成清单：服务是否在运行（必须是 `start` 启动的才能自动停止）、数据库实际读到的引擎 / 主机 / 库名 / 表数 / 行数（估算）/ 大小、缓存里本系统前缀 `nex:*` 的 key 数（memory 缓存不处理）、`data/uploads` 的文件数和大小；任何一项读不到就中止。
- 默认先用本机的 `mysqldump` / `pg_dump` 备份，格式与备份页完全一致：写到 `backup.dir`（与备份页、`restore` 同一个目录，不再写死 `./backup`），文件名 `nexadmin-reinit-<引擎>-v<框架版本>-<yyyymmdd-hhmmss>.sql.gz`，gzip 压缩，旁边有 `.sha256` 旁路文件，目录 0700、文件 0600。所以可以直接交给 `restore` 恢复（`restore` 是否识别由 `.sql.gz` 后缀、`SafeBackupName` 命名规则和 sha256 校验决定，单测里用假 `mysqldump` 验证过这条链路）；找不到工具时清单写明未备份，由你决定是否继续。`--dry-run` 只列清单，不备份不执行。
- 确认默认 N，只有 `y` 才执行；`app.env=production` 时再输入库名。
- 执行：停服务 → 删除库内所有表 → 清缓存 `nex:*` → 删除 `data/uploads` → 删除 `data/.initialized` → 自动启动，并提示向导里数据库配置按旧值填写。已完成的步骤失败后不回滚，处理后重新运行即可。
- 不动：`config/config.yaml`、`internal/`、`migrations/business/`、日志、远程对象存储里的文件（需要手工清理）、`data/secret.key`、`data/jwt.secret`。

reinit 全流程依赖真实数据库，本机只实测了 `--dry-run` 在无 `config/config.yaml` 时的拒绝，其余未实机验证；备份文件的命名、gzip + sha256 格式和 `restore` 的识别有单测（用 PATH 里的假 `mysqldump`），真实 `mysqldump` / `pg_dump` 导出与导入未实机验证。

## 9. 监控

### 9.1 /healthz

`GET /healthz`（根路径，不登录，供负载均衡和容器探针使用）。已初始化：对数据库做一次 `Ping`，成功返回 HTTP 200 `{"code":0,"message":"ok","data":{"status":"ok"}}`，失败返回 503（统一错误体）。未初始化时只报告进程存活，恒为 200。注意它只探数据库，不探缓存、存储和迁移——这些在下面的健康详情里。

### 9.2 /metrics

`GET /metrics`（根路径，Prometheus 文本格式，`Cache-Control: no-store`），由 `metrics.enabled`（默认 `true`）和 `metrics.token` 控制：

- `token` 为空：只允许回环地址访问，且带 `X-Forwarded-For` 或 `X-Real-IP` 头的请求一律拒绝（返回 403）。所以本机的 Prometheus 可以直接抓；经本机反向代理转发的请求会被拒绝。
- `token` 非空：任何来源都必须带 `Authorization: Bearer <token>`，常量时间比较；缺失或错误返回 401 并带 `WWW-Authenticate`。
- `enabled=false`：不注册该路由。

指标（代码中的名字；本机未初始化状态下实测输出了前 11 项）：`nexadmin_http_requests_total{method,route,status}`、`nexadmin_http_request_duration_seconds`（histogram）、`nexadmin_http_requests_in_flight`、`nexadmin_cache_requests_total`、`nexadmin_cache_errors_total`、`go_goroutines`、`go_memstats_alloc_bytes`、`go_memstats_heap_inuse_bytes`、`go_memstats_sys_bytes`、`go_gc_cycles_total`、`go_gc_pause_seconds_total`；已初始化后还有 `nexadmin_db_connections_{open,in_use,idle,max_open}`、`nexadmin_db_wait_total`、`nexadmin_db_wait_seconds_total`、`nexadmin_migrations_pending`、`nexadmin_migrations_check_ok`、`nexadmin_job_queue_length`、`nexadmin_plugin_licensed`（后几项依赖对应模块，已初始化后的输出未实机验证）。

### 9.3 健康详情

“系统管理 → 服务监控”（模块 `server-monitor`，权限码 `serverMonitor:list`）：

- `GET /api/v1/monitor/health`：并发检查 `db`、`cache`、`storage`、`migrations`、`plugins`、`disk` 六项，每项独立 3 秒超时，整体状态取最差的（`ok` < `warn` < `fail`）。规则：数据库慢于 500ms、缓存慢于 200ms、存储慢于 1500ms 为 `warn`；有待执行迁移 `warn`；插件授权已过期 / 无效 / 30 天内到期 `warn`；磁盘使用率最高的分区 ≥85% `warn`、≥95% `fail`。
- `GET /api/v1/monitor/server`：CPU、内存、磁盘、网络、Go 运行时（Linux 读 `/proc`，其他系统只有运行时信息）。
- 另有缓存监控（`cacheMonitor:list`，`cache-monitor`）和接口监控（`apiMonitor:list`，`api-monitor`：最近 30 秒各接口 QPS、平均耗时、错误率，进程内统计，重启清零）。

### 9.4 前端错误上报

前端把运行时错误 `POST /api/v1/client-errors`（登录与否都可上报，按 IP 限流，规则 `ratelimit.client_error`，默认 30 次/分钟；请求体上限 8KB，字段服务端再截断）；管理员在服务监控页的“前端错误”标签用 `GET /api/v1/monitor/client-errors`（权限码 `serverMonitor:list`）查看。记录保留 14 天，每小时清理一次。

### 9.5 日志

`app.env=dev`：控制台输出；`production`：JSON 输出到 stdout 和 `logs/nexadmin.log`，没有内置轮转，需要自己用 logrotate 等处理（`copytruncate` 的效果：未验证）。`start` 启动的进程控制台输出另存 `logs/nexadmin.out`。每个请求一条日志（含 method、path、status、latency、ip）。

## 10. 多实例注意事项

下面每条都来自代码或代码注释：

- `database.node_id` 必须各不相同（雪花 ID 节点号 0–1023；导出中心也用它区分节点）。redis 缓存下启动时会用带 TTL 的租约（30 秒，每 10 秒续约）检测重复：发现被别的存活实例占用就拒绝启动并报错；实例崩溃后用同一个 node_id 重启，最多会被拒绝 30 秒。`memory` 缓存（单实例）下不检测。
- 必须用 `cache.driver=redis`：令牌吊销、验证码、登录失败锁定、限流计数、在线会话都在缓存里；`memory` 是进程内的，实例之间互相看不到（例如在实例 A 登出的令牌在实例 B 仍有效，验证码在 A 生成、B 校验会失败）。
- `auth.jwt_secret` 所有实例必须一致：留空时每个实例读写各自的 `data/jwt.secret`，要么共享这个文件，要么显式配置同一个值。`data/secret.key`（或 `NEXADMIN_SECRET_KEY`）同理，加密的值要能互相解密。
- 迁移靠数据库锁串行，多实例同时启动安全；备份、导出任务靠乐观抢占，不会重复执行。
- 已原子化（多实例下并发也只有一个成功；代码注释已写明）：
  - 一次性凭据的“取出并作废”：SSO 授权码兑换、短信验证码与忘记密码验证码的校验成功、第三方登录的 `state`、待绑定令牌（`bindToken`，在账号密码校验通过后、写入绑定前消费）。登录图形验证码（`core/auth/captcha.go`，无论对错只能校验一次）也是同样的做法。统一走 `cache.GetDel`：redis 用 Lua 脚本在服务端一次完成 GET+DEL，memory 在同一把锁内完成。外部自定义的缓存实现如果没有实现可选接口 `cache.AtomicGetDel`，会回落为 Get 再 Del（非原子）并记一次 warn。
  - 套餐额度“先数后插”：用户（新增、导入、第三方登录自动建号）与角色的创建，在同一事务里先对租户行 `SELECT ... FOR UPDATE` 再统计数量，同一租户的并发创建被串行化，不会超出 `maxUsers` / `maxRoles`。额度为 0（不限）、默认租户和平台级操作不加锁、不多一次查询。
  - 错误次数计数：短信验证码输错（`modules/internal/smscode`）、忘记密码验证码输错（`modules/system/user`）、待绑定令牌尝试（`modules/internal/oauthflow`）、登录失败计数（`core/auth/captcha.go`，用户名与 IP 两个维度）以及短信的每日 / IP 每小时发送上限，都改为 `cache.Incr` 原子自增（辅助函数 `core/cache/incr.go`，首次创建时设 TTL，redis 用 Lua 脚本）。验证码类先自增再比对，所以并发猜测最多只有前 5 次会被比对，达到上限用 `Del` 作废验证码；计数 key 带验证码盐，重新发送即从 0 开始。语义不变（5 次作废、60 秒冷却、每日上限）。唯一的差别：登录失败计数的 15 分钟窗口从第一次失败起固定，不再随每次失败顺延。缓存不实现 `cache.Counter` 时回落为进程内加锁的 Get+Set（记一次 warn），此时多实例下计数不精确。
  - 存储额度已在创建 tus 上传会话时按声明长度原子预占（`modules/file/usage.go`），检查实际用量与在途预占之和，完成或取消后释放，并以租约清理过期预占。受限上传要求缓存支持 `cache.Lease`，不支持则拒绝；多实例必须共用 Redis/Valkey，memory 只适合单实例。真实共享缓存并发验收仍待执行。
- 仍存在的并发窗口与限制（代码注释已写明）：
  - 在线会话已改成“每会话一个 key + 有序集合索引”，不再读-改-写整份索引，并发登录不丢会话、强退只影响目标会话。残余窗口：同一会话被两个实例同时登记时后写者胜（只丢展示用的活跃时间 / 令牌 jti，下次登记纠正）；清理过期索引项时，若恰有并发登记重建了该会话，索引项可能被误删，列表里短暂缺失到该会话下一次登记；缓存没有有序集合能力时退回进程内存储，多实例下彼此不可见（内置 memory / redis 都支持）。
  - 站内消息 SSE 和租户变更失效事件通过 `core/cluster` 的广播总线跨实例传递（redis 用 Pub/Sub，断线自动重连并全量校正；memory 缓存下只在本实例）。该链路只在假实现和 miniredis 上验证过，没有在真实多实例 + redis 上验证。
  - 租户信息（到期、额度）仍有 30 秒进程内缓存兜底，但租户被修改后会广播失效事件，其他实例通常立即生效；广播丢失时最多延迟 30 秒。
  - 缓存故障时限流一律放行（fail-open）并告警；令牌校验则相反，缓存不可用时拒绝放行。
- 未验证：真实多实例拓扑下的整体行为；`cache.GetDel` / `cache.Incr` 的 Lua 脚本与额度的 `FOR UPDATE` 行锁只在 memory 缓存 / sqlmock 下验证过语句与顺序（本机没有数据库和 redis）。

### 11.1 反向代理必读

服务有两种“地址”，用途不同：

- **真实客户端 IP**（`c.ClientIP()`）：由配置项 `server.trusted_proxies`（IP / CIDR 列表）决定，默认空 = 不信任任何代理，只用 TCP 对端地址，伪造的 `X-Forwarded-For` / `X-Real-IP` 无效。配置后，只有对端地址在列表内的请求才会采信转发头，并取其中**最右一个不在列表内**的地址（代理依次追加，最右是最近一跳之前的真实来源；客户端自己塞在最左的假地址不起作用）。它用于：所有按 IP 的限流（登录、验证码、短信、令牌、前端错误上报、开放平台失败计数、SSO 令牌）、登录日志 / 操作日志 / 在线会话里的 IP、开放应用的 IP 白名单、忘记密码的 IP 限流。热挂载的插件子引擎也使用同一份配置。
- **TCP 对端地址**（`RemoteAddr`）：用于“是不是本机”的安全判定，永远不看转发头也不受 `trusted_proxies` 影响：初始化向导的本机判定、`/metrics` 的回环判定、本机关停接口（`stop` 用）。

**反向代理部署必须配置 `server.trusted_proxies`**（例如同机 nginx 写 `["127.0.0.1"]`，容器网络写对应网段，环境变量 `NEXADMIN_SERVER_TRUSTED_PROXIES=127.0.0.1,10.0.0.0/8`），并让代理设置 `X-Forwarded-For`（nginx 的 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`）或 `X-Real-IP`。不配置时的后果（未实机验证，来自读代码与单测）：

- 所有按 IP 的限流都以代理地址计数，所有用户共用同一个桶，默认的 `ratelimit.login`（20 次/分钟）会被全站共享。
- 登录日志、在线会话里记录的 IP 是代理地址；开放应用的 IP 白名单比对的也是代理地址。
- 配置后，列表里的地址要写对：写得太宽（例如把公网段写进去）会让该网段的任何人伪造来源 IP；代理必须覆盖或追加转发头，而不是原样透传客户端自带的头。
- 初始化向导：同机反向代理转发来的请求对端是 `127.0.0.1`，但带有转发头，向导**不再把它当成本机**，默认拒绝；要经代理初始化，需设置 `setup.allow_remote=true` 并带 `X-Setup-Token`，或者直接用 `init --config`。
- `/metrics` 在未配置 token 时只认回环**对端**且不带 `X-Forwarded-For` / `X-Real-IP` 的请求，经代理抓取要配 `metrics.token`。

代理配置要点：

- 上传是 5MB 分片（前端 `CHUNK_SIZE = 5MB`，tus 的 `PATCH`），`client_max_body_size`（nginx）之类的请求体上限不能小于分片大小，上传路径建议关闭请求缓冲。应用层的大小 / 类型限制来自“系统参数”页的上传限制（保存后最多几秒生效，多实例最多晚 5 秒），页面没设的项回落到 `config.yaml` 的 `upload.max_size_*`（详见《配置参考》）。
- 站内消息的 SSE（`GET /api/v1/messages/stream`）响应已带 `X-Accel-Buffering: no`；代理的读超时要足够长，断线后前端会自动重连并退化为轮询（前端行为按设计文档，未单独核对）。
- 转发 `Host`：租户域名绑定、插件授权域名校验都读请求的 Host。

## 12. 升级

框架升级、二开项目升级的完整流程见《二次开发指南》第 1 节。运维侧要点：

```
nexadmin upgrade --from <新版本源码包目录或zip> --dry-run    # 只列变更；工作区不干净时 dry-run 只警告
nexadmin upgrade --from <新版本源码包目录或zip>              # 正式升级（工作区不干净会拒绝，除非 --allow-dirty）
go mod tidy && (cd web && npm install)                        # 合并 go.mod / package.json 之后
sh scripts/build.sh                                           # 重新构建
```

（`nexadmin` 指 `go run ./cmd/nexadmin`，或自行编译的 `cmd/nexadmin`。`upgrade --from ... --dry-run --allow-dirty` 在本机用 `nexadmin new` 生成的演示工程上实测过，输出 `摘要: 新增 0，修改 0，删除 0，未变 958，WARN 0`。）

升级后的服务端动作：

- `app.auto_migrate=true`：重启即自动执行新增的框架迁移并补种新菜单（日志提示 `新增 N 个菜单，请到角色管理分配`——新菜单只有超管可见，其他角色要在“角色管理”里分配）。
- `app.auto_migrate=false`：先 `nexadmin-server migrate --dry-run` 看清单，再 `nexadmin-server migrate`，然后启动。
- 容器：重新 `docker build`，入口脚本会用镜像里的 `default.yaml` 覆盖卷里的 `config/default.yaml`，`config/config.yaml` 不动。
- 吊销清单（`config/license-revoked.json`）与附加公钥（`config/license-keys.pub`）由发行方随升级包分发，升级时按框架区覆盖；吊销清单自带 seq 回退保护（验签通过但 seq 小于当前已采信版本的清单会被忽略并告警，该保护只在进程运行期内生效，重启后以磁盘文件为准）。升级包里没有这两个文件时保留现有文件，不会移入 `.nexadmin-trash/`，`--dry-run` 清单里标为 `K`。
- 出厂数据的规则是“按业务键不存在才插入，已存在一律不动”：新版本改了某条出厂数据时，存量库不会自动跟着变，需要管理员在后台手改。

| 现象 / 报错 | 原因 | 处理 |

| `migrate: 等待迁移锁超时（2m0s），另一个实例可能仍在迁移` | 别的实例持有迁移锁超过 2 分钟 | 确认其他实例是否卡住；MySQL 的锁是 `nexadmin_migrate_<库名>`，会话断开自动释放 |
| `cache: redis/valkey at <地址> is unavailable: ...` / `config: cache.addr is required when cache.driver is redis` | 缓存连不上 / 没配地址 | 核对 `cache.*` |
| `auth: auth.jwt_secret must be at least 32 characters` | 显式配置的 JWT 密钥太短 | 至少 32 字符，或留空让程序自动生成 |
| `secret: key from <来源> must be 32 bytes encoded as hex (64 chars) or base64` | `NEXADMIN_SECRET_KEY` 格式不对 | 用 32 字节的 hex（64 字符）或 base64 |
| `core: duplicate module name "xxx"` | 业务模块或插件与内置模块重名 | 改业务模块的 `Name()`（同时改权限码前缀和表前缀） |

| 登录后接口 HTTP 403，`reason: TENANT_EXPIRED` | 租户已过期 / 已停用（超出宽限期） | 在租户管理里续期或启用；租户信息有 30 秒缓存兜底，多实例下修改会广播失效（第 10 节），最多 30 秒后生效 |
| HTTP 429，`Retry-After` | 触发限流 | 见《配置参考》第 6 节；经反向代理时见第 11.1 节 |
| `服务在运行，但不是由 start 启动的（没有 pid 文件），请到它所在的终端按 Ctrl+C 停止` | 前台运行的进程没有 pid 文件 | 在它的终端按 Ctrl+C |

| `进程已退出（<原因>），详见 logs/nexadmin.out` / `等待 服务启动 超时` | `start` 拉起的后台进程启动失败或 20 秒内没就绪 | 看 `logs/nexadmin.out` |
| `服务正在运行，已拒绝恢复；请先执行 stop 停止服务（恢复会覆盖线上数据）` | `restore` 前没停服务 | 先 `stop` |
| `找不到 <备份文件>.sha256，无法校验完整性；可用 --sha256 <值> 手工提供，已中止` | 备份缺旁路校验文件 | 补回 `.sha256` 或用 `--sha256` |
| `本机未找到 mysqldump / mariadb-dump，请安装对应数据库客户端工具并加入 PATH` | 备份 / reinit 备份需要的客户端工具不在 PATH | 安装客户端工具；容器镜像默认不带 |
| 启动日志 `file module disabled: storage init failed` | 文件模块的存储初始化失败（例如 S3 配置、`${ENV}` 未设置） | 看同一行的错误；文件模块的路由此时没有注册 |
