### Login methods

The login page shows methods per configuration; unconfigured ones are absent without errors (`GET /api/v1/auth/methods` returns `methods`, `providers`, `registerProviders`, `forgotEnabled`). All three methods issue the same JWT dual-token pair on success.

| Method | Enabled when | Rules (from code) |
| --- | --- | --- |
| Password | `auth.methods` contains `password` (default) | The captcha switch in Settings → Sign-in security (`captchaEnabled`, on by default, effective immediately on save): when on, every password sign-in passes a captcha first (slider tier) and **escalates to the click captcha after 6 failures**; when off, sign-in, self-registration and anonymous SMS code requests show no captcha at all (sign-in remains bound by IP rate limits and account lockout) (failures include wrong passwords; slider drag misses also count toward the IP-side escalation counter — slider-grinding automation escalates too, and the escalation takes effect immediately: once a drag miss pushes the IP counter past the hard threshold, the verify-failure response itself carries `CAPTCHA_REQUIRED_HARD` and the frontend switches to the click captcha on the spot, without waiting for the next wrong password; while lockout only counts wrong passwords per username, so clumsy humans never get locked; `GET /auth/click` issues it, `POST /auth/click/verify` submits: a 384×150 master image with distractor characters plus a thumbnail strip of the 2–3 characters to click in order; dot positions stay server-side, each click is checked within its per-character tolerance, at most 5 verify attempts per challenge). The default form is the slider puzzle (`GET /auth/slider` issues it, `POST /auth/slider/verify` submits): a single notch is cut in a 384×150 backdrop (its X is retried into the legal range; flush with the sign-in form, scaled proportionally on narrow screens), and the piece must be dragged into it, after which a one-time token is written under the same cache key as the digit captcha, so the password, SMS and register paths all consume it through the same `VerifyCaptcha` gate (IP-bound, single use; issued tokens carry a form marker — slider `s|`, click `c|`, digit text unmarked); **the login hard tier verifies through `VerifyCaptchaHard`, which accepts only point-click (`c|`) tokens** — slider tokens and digit text are refused, so a script that calls `/auth/slider` directly is stopped server-side rather than merely by the front-end form; the hole's X is never derived from the client-visible key (the hand-drawn fallback draws it from `crypto/rand`), and the trail is checked too (≥6 points, 150ms–15s, ≥40px of travel, ±6px landing tolerance, plus speed-profile gates on multi-point trails — speed dispersion and a teleport cap), at most 3 verify attempts per challenge (a missed drag immediately issues a new challenge). Both forms draw from a pool of 21 backdrops, and every challenge adds a random tone perturbation (the same operation over backdrop and piece), defeating pre-labelled image libraries. The slider interaction runs on rc-slider-captcha (MIT) as an inline panel: the puzzle panel and drag bar live in the form flow, collapsing to a one-row badge after passing ("verify again" loads a new challenge); all three forms carry a top-right refresh button. The frontend only binds the backend contract; the form is assigned by the server based on risk and cannot be downgraded by the user (the click tier cannot be switched away) — the only exit in the UI is "switch to the digit captcha" (typeable, with audio, the accessibility fallback), and from there "switch back" to the assigned form; **in the hard tier the server accepts only click tokens, so digit text is refused** until the failure counter's fixed 15-minute window expires — an availability-for-security trade-off that removes the slider bypass. Ops metrics are exposed via `/metrics`: `nexadmin_auth_captcha_issued_total` / `verify_pass_total` / `verify_fail_total` (by image/slider/click) and `escalation_total` (by slider/click tier). One click switches to the digit captcha (5 digits, 224×72 glyph rendering with random scaling, per-digit skew and wave distortion, 60 seconds, one-time; `GET /auth/captcha/:key/audio` returns the same captcha as audio — it only reads, never consumes, and the voice follows the UI language, zh / en). Repeated wrong passwords lock the account; fallback is 5 failures / 15 minutes, while the factory lock-duration parameter is 30 minutes, adjustable in the settings page `security` section or system params `login.max_retry` / `login.lock_minutes`; when the user doesn't exist a bcrypt comparison is still performed and the response uniformly says "wrong username or password" — the real reason only goes to logs; lockout treats existing and non-existing usernames identically, and lockouts are persisted in `sys_login_lock` (per tenant + username, expired rows swept at most hourly on the next lock creation) with cache as the fast path: a locked account still rejects the correct password after a restart or on another instance |
| Phone | `auth.methods` contains `phone` and `sms.provider` is non-empty, otherwise hidden | The phone must already be bound to an account; codes are valid 5 minutes, one SMS per phone per 60 seconds, max 10 per phone per day, max 10 per IP per hour, 5 wrong entries void the code |
| Third-party quick login | `auth.providers.<name>` fully configured, or enabled and completed in Settings → Sign-in methods (read per request, effective on save) | OAuth2 authorization code flow: WeCom, DingTalk, Feishu, Google (OIDC, code + PKCE), GitHub, generic OIDC (Keycloak, Casdoor, etc.). `state` is one-time and callback URLs are exact-whitelisted; first login matches existing accounts by `match_by`, unmatched accounts are told to "bind an existing account", and `auto_create: true` auto-creates; only verified emails count; binding/unbinding is available in Profile |

Third-party config keys are in the Configuration Reference §3. The frontend callback page is `/admin/login/oauth/<provider>`; `redirect_uris` must be its full URL — that is exactly what Settings → Sign-in methods → Redirect URIs asks for, prefilled with the current site's address when a provider is enabled. Google / GitHub need outbound internet; configure `auth.proxy` on restricted networks.

- **Settings → Sign-in methods is a runtime source (wired 2026-11-13)**: the password/phone toggles, provider toggles and credentials, redirect URIs, WeCom AgentId, matching rules and outbound proxy are stored in `sys_setting.auth`, read per request, and take effect on the next login-page load without touching `config.yaml` or restarting. `config.yaml` becomes the fallback/seed: when the section was never saved everything follows the file; a saved provider only overrides the fields it filled (an empty secret keeps the file/env value), and turning it off disables it even if the file configures it. `GET /settings` hydrates providers configured in the file as enabled (secret left empty), so admins can see and switch them. Saving validates with the same merge rules: an enabled provider still missing `client_id` / `client_secret` / `redirect_uris` (plus `agent_id` for WeCom, `issuer` for OIDC) is rejected (`config.auth.provider_incomplete`), and so is leaving no sign-in method at all (`config.auth.no_login_method`) — no more "saved successfully, nothing on the login page". Provider adapters are cached by a config fingerprint, so changed credentials/endpoints/proxy rebuild them on the next authorization instead of redeeming codes with a stale client_id.

The register page (reachable once `auth.allow_register` / the `user.register_enabled` system parameter is on) shows the same row of buttons under the register button as "quick sign-up", listing every configured provider — `registerProviders` from `/auth/methods` (equal to `providers` while self-registration is open, empty otherwise). Two registration paths coexist: username and password go through `POST /auth/register`, while a provider button goes through `GET /auth/oauth/<provider>/start?intent=register`.

- **The register intent lives in the server-side state** (`oauthflow.PurposeRegister`) and cannot be forged by the client: `start` checks the same runtime switch as `/auth/register` (404 when closed) and rate-limits by IP to 10 per hour (the `oauth_register` bucket, shared across providers and counted separately from password registration).
- On the way back, `resolveLogin` still honours an already-bound identity first and then `match_by` against existing accounts; when neither matches it **creates the account** instead of answering "bind an existing account", and it is **not gated by the provider's `auto_create`** — that switch only governs auto-creation on the login side.
- Creation obeys the same constraints as self-registration: the tenant plan's user quota (`ensureUserQuota`), a passwordless account (no password sign-in; use the provider afterwards or set a password in Profile), roles from `auth.register_roles` (same as password registration, **not** the provider's `default_role`), and the same `user.created` event on success.
- If an administrator turns self-registration off mid-authorization, the register intent in the state lapses and the flow falls back to login semantics (no account is created), so a user who already authorized is not left stranded.

- **Re-run recipe for the quick sign-up chain against a live backend (run and passed 2026-11-10)**: a throwaway database, a CWD outside the repository and `NEXADMIN_SERVER_PORT=<free port>` (same recipe as the slider smoke test above), with a generic `oidc` provider in `config/config.yaml` pointing at a local stub IdP, `auto_create: false` and `register_roles: [guest]`. Three traps in the stub IdP: (1) it must serve `/.well-known/openid-configuration` — without it `Flow.adapter` fails with `ErrNotConfigured` and `start` answers 404, which looks like "the register switch is off"; (2) the id_token's ES256 signature needs `dsaEncoding: 'ieee-p1363'` (Node defaults to DER, JWS wants raw R‖S, otherwise `crypto/ecdsa: verification error`); (3) persist the private key across restarts — the adapter caches JWKS by `kid` for an hour, so a new key is judged invalid. Measured: `registerEnabled` comes from the `user.register_enabled` system parameter (`sys_config` seed id `7300000000010000005`), with YAML `auth.allow_register` only as the fallback when the row is missing; once on, `registerProviders` equals `providers`; `start?intent=register` then callback returns `{accessToken,refreshToken,user}` (the account is created even with `auto_create: false`, role `guest`, `/auth/me` works), while the same provider without `intent` still returns `{needBind}`; turning the switch back off mid-authorization makes that state's callback degrade to `{needBind}` with no account; while closed, `start?intent=register` answers 404; 11 consecutive `start?intent=register` calls give 10×200 then 429.

- **Slider interaction belongs to rc-slider-captcha (MIT); three traps are pinned down (2026-11-06)**: (1) the component fires `request` only on mount when `autoRequest` is true, or through an explicit `actionRef.refresh()` - with neither, the track renders but the puzzle never loads, which locks login once three wrong passwords force the captcha; images now load on their own because a new challenge `key` remounts the component. (2) rc maps handle travel to puzzle travel by `ratio = (bgW - puzzleW) / (bgW - buttonW - 2)` (280/63/40 -> 217/238), so "handle pixels = image pixels" is false (measured: 184px of mouse travel moved the puzzle 167.75px); every width is read from the live DOM. The submission uses the same coordinate system: rc records absolute clientX in its trail, which would make the backend's "at least 40px of travel" rule measure page coordinates, so the trail is shifted to a zero origin and scaled to the landing. The time axis was later switched from "spread linearly over the total duration" to real `pointerdown/move` sampling (`sliderTrail.ts`: used once there are at least `TRAIL_MIN_SAMPLES` = 6 samples, with the linear spread kept only as a fallback) - a linear spread can never put more than `duration / points` between samples, so it cannot reproduce a human's mid-drag pause, so a human's mid-drag pause must still pass. Migration leftovers are gone too: the `actionRef` that was passed but never used, the unused `IMG_W`, and the stale `imgH` fallback 120 back to the factory 110. (3) `puzzleSize.height` is a field the library documents; leave it out and its documented default - "height equals the background height" - stretches the 63×63 piece image to 63×110 (`object-fit` defaults to fill), so the piece reads as a squashed white outline that never lines up with the hole. Horizontal travel is unaffected, so the drag still works and still verifies - only the picture is wrong (measured: rendered box 63×110 against a 63×63 source). The height now comes from `pieceHeight` in the response (`pieceWidth`'s fallback also moved from the library's default 68 to the factory 63). Keyboard support was removed by product decision; the accessibility fallback is the digit captcha (typeable, with audio). One line on attribution: the first half of this lane (the rc migration and the e2e rewrite) was swept on 2026-11-06 into five mixed commits from concurrent sessions - `27a9804`, `f82ae40`, `e1adb60`, `68515d9`, `03d403b` - while the second half - the coordinate normalization and the evidence gate - is `70953b3`, and these two documentation records are `f927fa9` and later; pushed history is not rewritten, so read those numbers together instead of expecting one lane-sized commit.
- **Recipe for the live-backend chain (run and passed this round)**: `cd web && npm run build` -> `go build -tags embedweb -o <temp dir>/nexadmin-server` (one process, one origin, which sidesteps the false reds of vite dev plus go run) -> `nexadmin-server init --config <one-off params>` with a throwaway database name, `NEXADMIN_MIGRATIONS_DIR` pointing at `migrations/framework`, and CWD outside the repository so `config/config.yaml` and `data/` stay untouched -> start it with `NEXADMIN_SERVER_PORT=<free port>` -> in the browser, locate the hole in the real PNG backdrop as the darkest 52x52 window and drag using the same ratio. Measured: `POST /auth/slider/verify` answers `code:0` and issues a token, the reported trail is `{first:0, max:106, last:106, n:15}` (landing 106, tolerance +/-6), then `POST /auth/login` returns 200 and the SPA leaves `/login` - the slider token really is consumed by the login `VerifyCaptcha` gate. This smoke test needs a throwaway database and a local port, so it is not part of CI and no spec file was left behind (one without a consumer is dead weight).

### Tokens & sessions

- Access token (default 30 minutes) and refresh token (default 168 hours), HS256; refreshing revokes the old refresh immediately; logout revokes the current access and its paired refresh; revocation records live in cache, and cache unavailability rejects requests.
- Optional `auth.single_session: true`: only the latest login's tokens are accepted for the same tenant+user; old access/refresh tokens are rejected, and refresh uses an atomic compare-and-swap so old sessions cannot overwrite new logins. Off by default; multi-instance requires shared Redis and identical configuration.
- Users of expired / suspended tenants cannot log in, cannot refresh, and their active requests are rejected too (§6).
- Forgot password (`POST /auth/forgot/send-code`, `/auth/forgot/reset`): uses available email / SMS channels and account bindings; codes last 10 minutes, with a 60-second cooldown, at most 5 attempts, and per-IP/per-account hourly limits. Non-unique email or phone bindings among enabled accounts cannot use recovery; account existence is not disclosed and an admin must reset the password.
- Online sessions are passively registered: logged-in requests record "user + IP + UA" into cache; force logout revokes the token of that session's last-seen entry.
